AVAL Store Pre-Launch Audit

Next.js 16.4.3 · React 19.3 · Prisma 6 on Supabase PostgreSQL · branch abish (with uncommitted Postgres migration) · audited 17 Nov 2026

A. Overall assessment

4/10
Overall quality
Not ready for production. The storefront looks good and the backend design document is strong, but the live order flow (the "enquiry" flow) trusts prices sent by the browser, exposes customer addresses and phone numbers to anyone holding or guessing a link, lets anyone post chat messages as the admin, and can mark orders as paid without a payment. The checkout page also crashes on any validation error.

Maturity: late prototype / early alpha. The UI is close to design-complete; the backend has two competing order systems, one of which (the documented Order/Payment/Coupon pipeline) is not connected to the storefront at all. Much of the storefront and admin still falls back to hard-coded mock data, which hides real failures.

Major strengths

  • Distinctive, on-brand visual design with a consistent maroon/gold palette and good product photography direction.
  • Thoughtful backend design doc: integer paise, snapshots, idempotency keys, state machines, outbox email.
  • Prisma schema is well-indexed with sensible relations and audit/outbox tables.
  • Zod validation on most write routes; RBAC permission matrix; bcrypt (cost 12) passwords; httpOnly session cookie with DB-backed revocation.
  • Low-friction checkout concept (no account, WhatsApp link) fits the target customer.
  • TypeScript type-check passes cleanly.

Major weaknesses

  • Server trusts client prices in the order flow that is actually live.
  • Order privacy depends on a browser-only check; track-order leaks orders by partial phone match.
  • Admin credentials shown on the login page; development auth bypass on 8 admin APIs.
  • Mock data silently replaces real data across storefront and admin.
  • Coupons, shipping and stock are inconsistent between banner, cart, checkout and server; stock is never decremented for enquiries.
  • Checkout crashes on server validation errors; hydration errors on every page once the bag has items.
  • Half the backend (Order/Payment/pricing engine/cron) is dead code with a fake Razorpay order id.

D. UI/UX improvement report

Visual consistency

The palette (maroon --pr, cream backgrounds, gold accents) and the serif display face are applied consistently, and the brand feels premium. The weaknesses come from implementation: 1,343 inline style={{}} objects mean spacing, font sizes and radii drift page to page (for example 32px, 34px and 28px page titles; 11px–15px body text). Emoji are used as icons next to SVG icons (🌸 📦 💎 vs line icons in the header), which mixes two visual languages. Move to a small set of shared components (Button, Input, Field, Card, Badge, SectionHeader) driven by the existing CSS variables in globals.css, and replace emoji with the same line-icon set.

User experience

  • Trust copy contradicts behaviour. Cart promises Razorpay payment; checkout actually sends an enquiry and payment happens later after a chat. Say so plainly on the cart ("Place order now, pay by UPI after we confirm your design").
  • Prices change between steps. Coupon and shipping disappear at checkout. Show one order summary computed by the server at every step.
  • Navigation duplicates. "Track Order" appears twice in the desktop header; "Customised" vs "Custom Order" are easy to confuse. Merge into "Personalised" (catalogue) and "Design Your Own" (request).
  • Desktop header is cramped at laptop widths (labels wrap onto two lines at ~1000px). Collapse to the mobile drawer earlier or shorten labels.
  • Empty/test data is public: the "key chain" category with 0 items. Hide categories with no active products.
  • Error handling: errors should name the field ("Enter a 10-digit WhatsApp number"), not show a crash or a generic message.
  • Account page auto-redirects after 1.5s, which is disorienting. Either remove the link or make it a clear "Find my order" page.

Responsive design

Mobile checkout and admin orders lay out well. The home page overflows horizontally on both ~1000px desktop (category tiles) and 375px mobile (drawer and hero), producing a sideways scroll. The mobile bottom nav covers the end of long pages; add bottom padding equal to its height plus env(safe-area-inset-bottom). 21 tap targets on the mobile home page are under 32px.

Accessibility

  • Form labels are not associated with inputs (<label> without htmlFor), so screen readers announce placeholders like "9876543210" as the field name.
  • Quantity buttons "−" and "+" have no accessible names; add aria-label="Decrease quantity".
  • .input sets outline:none and relies on a border colour change; the global :focus-visible rule helps, but verify every custom control keeps a visible ring.
  • Decorative emoji should carry aria-hidden="true".
  • Payment confirmation uses alert(); use an in-page status message with role="status".
  • Colour contrast of grey helper text on cream (--tx2) should be checked against WCAG AA 4.5:1.

E. Code & architecture review

Structure

  • Two order systems. src/server/orders/checkout.ts, src/server/pricing/engine.ts, /api/checkout/place, /api/payments/verify, /api/webhooks/razorpay, coupons and cron operate on Order; the storefront uses Enquiry. Admin Orders, Dashboard and Reports read Order, so they will always be empty for real customers. Pick one model. Recommended: keep the enquiry UX, but on enquiry creation price it with priceCart and persist through the Order/OrderItem tables (with a status for "awaiting confirmation"), so stock, coupons, reports and snapshots all work.
  • Mock data as fallback (lib/data.ts imported by 11 files). It hides API failures and lets customers order products that do not exist. Remove it from runtime code; keep it only in the seed script.
  • Pages are very large (app/o/[token]/page.tsx 878 lines, app/admin/products/page.tsx 838). Split into components and hooks; product-mapping code is copy-pasted in shop, category and product pages. Add one toProductView() mapper.
  • Client-rendered catalogue. Product and category pages are client components that fetch after load. Make them server components that query Prisma directly, return notFound() for unknown slugs and export generateMetadata.
  • Inconsistent API contracts. Some routes return {success,data}, enquiry routes return raw objects or {error: ZodIssue[]}. Use the existing ok()/apiError() helpers everywhere and always return a string error plus optional fieldErrors.
  • Business constants duplicated: ₹200 personalisation charge in 3 places, shipping rules in 3 places with different values. Read from Setting on the server only.
  • No middleware/proxy protecting /admin; the admin layout is a client component with no redirect.
  • Repo hygiene: 4 MB design mockup HTML in the root, 4.1 MB of prototype HTML served publicly from public/extracted, a stray JPG in the root, README is the create-next-app template, .env.example still describes MySQL and lacks DIRECT_URL, mysql2 still a dependency, ad-hoc test scripts without a runner.

Database

  • Migration history replaced (uncommitted): the two MySQL migrations are deleted and a new init_postgresql added. Fine for a fresh project, but commit it as one deliberate change and never apply it against an existing MySQL DB.
  • Enquiry.items is JSON with no product foreign key or stock movement: stock is never decremented for the live flow. Product snapshots should be stored, but alongside real productId references.
  • Order.orderNumber uses 5 random digits: collisions become likely after a few hundred orders (unique-constraint 500) and numbers are guessable. Use a DB sequence or 8+ char random IDs.
  • Order.couponCode is a free string; the per-customer limit in Coupon.perCustomerLimit is never enforced; usage limit is checked outside the transaction (race).
  • Redundant @@index on columns that are already @unique (email, slug, token, orderNumber, code).
  • Product.rating/reviewCount are denormalised but nothing recalculates them when reviews are approved.
  • Backups: Supabase daily backups depend on plan; document a point-in-time recovery plan before launch.

F. Security & performance report

Security findings are detailed in the list above under the SEC- IDs. Summary of the attack paths that matter most:

  1. Pay ₹1 for any order: post an enquiry with unitPaise: 100 (SEC-1), then pay through the normal Razorpay flow; the webhook confirms it without checking the amount (SEC-7).
  2. Read other customers' addresses: send {"query":"98"} to /api/track-order to get a token (SEC-3), then GET /api/enquiries/<token> (SEC-2).
  3. Phish a customer as the shop: post senderType: "ADMIN" messages with a payment link into their order chat (SEC-4).
  4. Log in as owner if the seed admin exists in production (SEC-6).

Performance

  • Product images are ~800–900 KB JPEGs served with raw <img>; switch to next/image with sizes, or pre-compress to WebP/AVIF at ~150 KB. Three products share one identical file and two others share another.
  • Catalogue pages render mock HTML on the server and refetch on the client: double work, layout shift and wrong prices for crawlers. Server components fix this.
  • Chat SSE polls the database every 1.5 s per open tab, holds a connection open indefinitely (incompatible with serverless timeouts) and can drop messages created between the query and the timestamp update. Use Supabase Realtime, or poll with the last message id as cursor.
  • The 4 MB prototype HTML under public/extracted is deployable and indexable.
  • Core Web Vitals were not measured: only a dev server was running and a production build was not attempted.

G. Missing features & product improvements

Essential before launch

  • Server-side pricing for enquiries, including coupons and shipping, shown identically in cart, checkout and the order page.
  • Stock reservation on order and release on cancellation.
  • Notifications: the checkout promises a WhatsApp link, but nothing sends WhatsApp or SMS, and enquiry creation queues no email. Customers who close the tab lose their only link. At minimum show the link prominently with a copy button and queue an email/SMS.
  • Admin authentication guard and a real admin user management screen (change password, add staff).
  • Error and empty states instead of mock fallbacks; a real 404 for products.
  • Legal pages: privacy policy, terms, returns/refunds (required by Razorpay onboarding and Indian consumer rules).

Valuable improvements

  • Photo upload on custom orders (the copy asks for saree photos; the form has no upload).
  • Reviews shown on product pages once approved, with the count computed from approved reviews.
  • Admin notification (email or push) on new enquiry and new chat message.
  • Product variants for size-specific stock if sizes sell out independently.
  • GST invoice generation once tax settings are confirmed with an accountant.

Scope & limits

  • Read-only audit. No source files, database records, configuration or packages were changed. I did not log in to the admin (it writes a session row) or submit a valid order, custom order or review, because each would write to the Supabase database.
  • Write-path findings (price tampering, webhook, coupon races, upload) come from code review and are marked as such. They are straightforward to confirm with one test enquiry if you allow it.
  • Only Chromium was available, so Firefox, Safari and Edge are untested. Performance numbers come from a dev server, not a production build.
  • Secrets in .env were not read (values redacted while inspecting). .env is correctly git-ignored.
